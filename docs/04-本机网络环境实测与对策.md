| `bgm.tv` 的 DNS | ❌ **被污染**（本机 `108.160.166.253` vs 真实 `128.242.240.157`） | 5 |

**⚠️ 一个关键提醒**：TCP 层探测在这里**会骗人**。
`Test-NetConnection github.com -Port 443` 返回 `True`，但真正的 HTTPS 请求 8/8 失败。
这是**基于 SNI 的 TLS 阻断**特征：TCP 握手被中间盒放行，TLS 阶段被重置。
**以后判断连通性，一律用 `curl` 发真实请求，不要信 `Test-NetConnection`。**

**关于 `github.com` HTTPS 的补充说明（多次复测，结论有修正）**：

| 时间点 | 结果 |
| --- | --- |
| 装 Git 时（winget 下载安装包） | ✅ 成功 |
| 随后连续测试 | ❌ **12 次请求全部失败** |
| 真实 IP 直连（`curl --resolve`） | ❌ 同样失败 → 排除 DNS 问题 |
| 数小时后再测（Clash Verge 运行中，但**无 TUN 网卡**、未设代理环境变量） | ✅ **返回 200** |

所以准确结论是：**`github.com` 的 HTTPS 是间歇性可达，不是永久封锁。**
同一时刻 `api.bgm.tv`、`google.com`、`raw.githubusercontent.com` 仍然全部不通，
说明不是代理在起作用，而是该域名的阻断本身时通时断。

**实践建议：不要把项目成败押在它的可用性上。**

- 「推代码用 SSH」这条建议**依然成立** —— SSH 通道实测始终稳定，且不依赖运气。
- `npm create astro` 也不必指望：本项目已手动搭好骨架，没有重跑它的必要。
- 如果哪天你发现直连 `github.com` 通了，那是正常波动，不代表问题已解决。

## 二、结论 1：`npm create astro@latest` 在你这台机器上用不了

### 实测报错（原文）

```
Error: Failed to fetch https://github.com/withastro/astro/tree/examples/minimal/
  at .../@bluwy/giget-core/src/utils.js:118
  [cause]: TypeError: fetch failed
    [cause]: Error: read ECONNRESET
```

### 为什么

`create-astro` 的模板**不在 npm 上，而在 GitHub 仓库里**。它的下载器 `giget` 会：
1. 先用 **HTTPS 访问 `https://github.com/withastro/astro/tree/examples/minimal/` 验证模板存在** ← **卡在这一步**
2. 然后才去 `codeload.github.com` 下 tarball（这个域名是通的，但根本走不到）

所以第 1 步被 SNI 阻断，整个命令就废了。**这不是你的操作问题，也不是网络"慢"。**

### 对策：手动建站（**已实测跑通**）

```powershell
mkdir my-blog
cd my-blog
npm init -y
npm install astro
npm pkg set scripts.dev="astro dev" scripts.build="astro build" scripts.preview="astro preview"
# 然后手写 astro.config.mjs 和 src/pages/index.astro（见下）
npx astro build
```

**实测结果**：
- `npm install astro` → `added 186 packages in 8s`
- `npx astro build` → `1 page(s) built in 489ms` → 产出 `dist/index.html`，内容正确

**一个 Astro 项目的最小构成只有 4 个东西**：

```
my-blog/
├── package.json          # 项目定义（依赖 + 脚本）
├── astro.config.mjs      # Astro 配置
├── src/pages/index.astro # 页面（路由即文件）
└── node_modules/         # 依赖（不提交）
```

### 🎁 意外的好处

**手动建站其实比 `npm create astro` 更适合你。** 官方模板会灌进来十几个文件
（README、`.vscode/`、`public/`、示例组件、配置文件……），新手根本分不清哪些是必要的。
手动建站你会亲眼看到：**一个能跑的 Astro 站，核心就是那 4 个文件。**

## 三、结论 2：阶段 6 必须用 **SSH** 而不是 HTTPS 推 GitHub

### 实测证据

```powershell
# HTTPS 方式：连不上
git ls-remote https://github.com/withastro/astro.git
# → fatal: unable to access ...: Failed to connect to github.com:443 after 21118 ms

# SSH 方式：服务器正常回应
ssh -T -p 22 git@github.com
# → git@github.com: Permission denied (publickey).   ← 这是成功响应！

ssh -T -p 443 git@ssh.github.com
# → git@ssh.github.com: Permission denied (publickey).   ← 也是成功
```

`Permission denied (publickey)` **不是失败**，它的意思是"TCP/TLS 都通了，服务器收到你的请求了，
只是你还没出示密钥"。这正是我们要的结果。

### ⚠️ 两个错误长得像，含义完全不同（新手极易误判）

实际用 `git` 命令时，你会看到下面**两种**报错之一，**它们的病因完全无关**：

| 报错 | 真正含义 | 怎么修 |
| --- | --- | --- |
| `Host key verification failed` | SSH **还不信任 github.com**（本地没有它的主机指纹）。**跟你的密钥、跟网络都没关系。** | 手动 SSH 一次并输 `yes`，或见下方命令 |
| `Permission denied (publickey)` | SSH 通道**完全正常**，只是你还没配密钥 | 生成并上传 SSH 公钥 |

**实测证据**（`git` 命令层面的最终确认）：

```powershell
git ls-remote git@github.com:withastro/astro.git
# 直接跑 → Host key verification failed.          ← 第一种
# 接受主机指纹后再跑 → git@github.com: Permission denied (publickey).   ← 第二种
```

看到第二种就说明**你离成功只差一把钥匙了**。别把它当成"连不上"。

### 对策（阶段 6 照做）

```powershell
# 0. 先让 SSH 认识 github.com（第一次会问 yes/no，输 yes）
ssh -T git@github.com

# 1. 生成密钥（一路回车即可）
ssh-keygen -t ed25519 -C "你的邮箱"

# 2. 打印公钥，复制全部内容
Get-Content "$env:USERPROFILE\.ssh\id_ed25519.pub"

# 3. 粘贴到 GitHub → Settings → SSH and GPG keys → New SSH key

# 4. 验证（应显示 Hi 你的用户名!）
ssh -T git@github.com

# 5. 仓库地址用 SSH 形式，不要用 https:// 形式
git remote add origin git@github.com:你的用户名/仓库名.git
```

### 备用通道（实测可达，关键时刻能救命）

| 通道 | 实测 | 用途 |
| --- | --- | --- |
| **Gitee 的 git HTTPS** | ✅ `git ls-remote https://gitee.com/mirrors/nginx.git` 成功返回 `HEAD` | 若 GitHub 彻底不可用，可先在 Gitee 建仓，再让 GitHub Actions 同步 |
| `ghfast.top` | ✅ 200 | 下载 GitHub 上的**公开文件/tarball** |
| `gh-proxy.com` | ✅ 200 | 同上 |
| `ghproxy.net` | ✅ 200 | 同上 |
| `gitclone.com` | ✅ 200 | `git clone` 公共仓库加速 |
| `hub.fastgit.org` | ❌ 000 | 已失效，别用 |

> ⚠️ **安全提醒**：这些第三方加速站只适合**下载公开内容**。
> **绝对不要**用它们来推送你自己的代码——那等于把代码和凭证交给陌生人。
> 推代码永远用 `git@github.com:...`（SSH 直连，实测可用）。

## 五、附带发现的三个 Windows 坑

这三个都会让你在**完全莫名其妙的地方**卡住，提前知道能省几小时。

### 坑 1：npm 11 的 install-scripts 审批门

装 `astro` 时会出现这个警告：

```
npm warn install-scripts 1 package has install scripts not yet covered by allowScripts:
npm warn install-scripts   esbuild@0.28.2 (postinstall: node install.js)
npm warn install-scripts Run `npm install-scripts ls` to review, or `npm install-scripts approve <pkg>` to allow.
```

npm 11 新增了安全机制：**默认不执行依赖包的安装脚本**。`esbuild` 的 `postinstall` 被跳过了。
实测**不影响 Astro 构建**（现代 esbuild 靠 `optionalDependencies` 分发二进制），
但如果以后某个包报奇怪的错，记得回来看这条。要用官方命令查看/放行：

```powershell
npm install-scripts ls
npm install-scripts approve esbuild
```

### 坑 2：Windows PowerShell 5.1 写文件会带 BOM，会让 `JSON.parse` 崩

你的默认终端是 **Windows PowerShell 5.1**（不是 PowerShell 7）。实测：

```powershell
Set-Content package.json -Encoding utf8   # ❌ PS 5.1 会写入 BOM (EF BB BF)
```

结果 Astro 构建时报：

```
Caused by: Unexpected token '', "{ "n"... is not valid JSON
```

**明明文件内容是对的，但 JSON 解析就是失败** —— 新手极难定位。

**对策（三选一）**：
- 改 JSON 别用编辑器/PowerShell 手写，用 npm 自己的命令：
  `npm pkg set scripts.dev="astro dev"`
- 或者写文件时用无 BOM 的 .NET 方法：
  ```powershell
  $U8 = New-Object System.Text.UTF8Encoding $false
  [System.IO.File]::WriteAllText("package.json", $content, $U8)
  ```
- 或者干脆**装 PowerShell 7**（`winget install Microsoft.PowerShell`），它的 `-Encoding utf8` 就是无 BOM 的

### 坑 3：`Get-Content` 看中文文件会乱码（文件其实没问题）

PS 5.1 的 `Get-Content` 默认用系统 ANSI 代码页（简中是 **GBK**）读文件。
所以读一个 UTF-8 的 `index.html` 会显示：

```
<title>鎴戠殑鍗氬</title>          ← 看起来像坏了
```

那是"UTF-8 字节被当成 GBK 解读"的经典乱码。**文件是好的，是读取方式的锅。**
正确读法：

```powershell
Get-Content index.html -Encoding utf8
# 或
[System.Text.Encoding]::UTF8.GetString([System.IO.File]::ReadAllBytes("index.html"))
```

**验证过**：实测产出文件的字节是 `e6 88 91 e7 9a 84 ...`（"我的"的 UTF-8 编码），
开头无 BOM，用 UTF-8 解码后中文完全正确。

> 💡 顺带一提：这正好是你学前端的第一课 —— **字符编码是真实存在的问题**。
> 后面写博客遇到中文乱码，90% 是编码链条上某一环错了。
